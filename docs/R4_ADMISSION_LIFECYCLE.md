Implementation direction: reuse the durable admission/pin documents themselves as the retry inventory, not another financial-data copy. Retry-enabled Firestore lifecycle events handle consumption and authority changes. A source-defined scheduled recovery scans bounded pages, with per-collection progress and isolated failures, so abandoned clients need not return. Explicit collection-group index configuration accompanies UID-scoped account cleanup. No TTL service or deployed scheduler is assumed.

The cleanup transaction re-reads the latest permit and matching pins; replacement tokens and valid in-flight writes must survive stale events. The existing retention/reset control fences new preparations while account cleanup removes temporary copies. Retention cannot report completion if this required deletion fails. Existing legacy R3 admissions and pins are in scope, not only newly tagged documents.

## Implemented runtime contract

- `receipt-admission-lifecycle.js`: `cleanupAdmission` atomically deletes the latest invalid/expired permit and its matching pins; `expectedToken` fences stale events. `cleanupPin` only removes an orphan or superseded pin, never a matching permit's protection alone. Neither function deletes Storage bytes.
- Retry-enabled admission events clean successful consumption/cancellation and invalid new proposals. Entitlement and partnership membership events re-read current authority, not historical event authority. Downgrade revokes pending Pro write permits, while original LTD historical reads remain unchanged for Plus.
- The existing source-defined `recoverReceiptCleanupJobs` schedule calls lifecycle recovery before receipt-job recovery. Each of the three collection groups has an independent 40-document page/cursor; per-item failure is retained for retry and does not prevent subsequent items/pages from progressing. Recovery covers legacy R3 documents and consumed orphan pins without R4 UID metadata. No client return or TTL setup is required.
- `firestore.indexes.json` explicitly includes collection-group UID indexes for account-scoped cleanup. Deploying App, Rules, Functions and required indexes together remains a separately authorised future rollout; no production scheduler/index deployment is part of this handoff. Provider delivery, IAM and real elapsed expiry duration are not claimed tested.
- UID-scoped retention clears all this user's temporary proposals before processing the retained ledger. Existing purging/failed retention and deleting/failed reset controls fence preparation transactionally. The client outbox is unchanged; a valid later write obtains a fresh permit. Admission deletion failure propagates as retention `failedStage: admissions`, never a false complete.
- Account reset physically removes this user's admissions including shared subcollections before deleting user data. Other members' proposals and authoritative records survive. A committed shared reference is sufficient to retain a receipt even if that member has another live proposal; only actual image destruction waits on pending proposals. This corrects the directly reproduced reset failure without weakening reference safety.
- Permission checks concern new authenticated server reads. Previously lawfully downloaded data cannot be remotely retracted from a client's cache; local outbox and backup preservation remain intentional. Final tests use server reads, actual document/pin existence and real Rules commits, not UI hiding or source regex alone.

The original independent R3 red report/probe/result is included byte-for-byte in R4 evidence. Early R4 development failures are separately labelled diagnostics, not accepted gates.
